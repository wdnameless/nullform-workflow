# Демо-приложение для тренировки

Промпты в этой папке рассчитаны на **ваш собственный проект** — в этом весь смысл.

Полигон нужен для другого: **увидеть, как проверка краснеет.** На своём проекте вы
поставите тесты и увидите зелёное — и не узнаете, ловят они хоть что-нибудь.
А специально ломать себе приложение вы не станете, и правильно.

Здесь для этого есть готовый скрипт: он вносит две настоящие поломки и откатывает обратно.

Заодно пригодится, если у вас другой стек или проекта под рукой нет, а посмотреть хочется.

## Промпт

Создайте пустую папку, откройте в ней агента и вставьте:

```
Собери маленькое веб-приложение — полигон для тренировки на тестах.
Стек: Next.js (App Router) + TypeScript + Prisma + SQLite. Никаких лишних
зависимостей, никакого UI-фреймворка, простая вёрстка.

ВЕРСИИ — ставь явно, `@latest` не используй: Next.js 15.x, Prisma 6.x, Node 22.
Если на момент чтения эти версии устарели — возьми последние стабильные,
но НЕ release candidate. Записанные версии положи в README.

АВТОРИЗАЦИЯ — самая простая своя: пароль через scrypt из node:crypto,
сессия — httpOnly-кука с подписью. Никаких next-auth, bcrypt, iron-session.

ЧТО ДОЛЖНО БЫТЬ В ПРИЛОЖЕНИИ

1. Вход по email и паролю. Регистрация. Ровно два заранее заведённых
   пользователя в сидах: anna@test.local и boris@test.local, пароль у обоих
   "test1234".

2. Личный список задач. У задачи: название, статус (active | done), владелец,
   дата создания. Пользователь видит ТОЛЬКО свои задачи.

3. Три действия, каждое СВОИМ файлом route.ts: app/api/tasks/list, /create, /delete.
   Не Server Actions и не один файл на три метода — так их проще ломать по отдельности.
   В каждом — проверка, что пользователь залогинен и что задача принадлежит ему.
   Удаление чужой задачи возвращает 404 (чтобы не подтверждать существование
   чужого id) — запиши это решение в README.

4. Лимит бесплатного тарифа: максимум 5 активных задач. Шестая — отказ с
   понятным сообщением. Расчёт лимита вынеси в отдельную чистую функцию
   в lib/limits.ts, без обращений к базе внутри неё.
   Добавь переключение статуса задачи active ↔ done — иначе слово «активных»
   в лимите не на чем показать.

5. Отрисовка списка — отдельным клиентским компонентом, который держит список
   в своём состоянии и сам решает, что показывать. Это важно: слой отрисовки
   должен быть отделён от серверного, чтобы их можно было ломать независимо.
   После успешного создания задача появляется в списке МГНОВЕННО, из состояния
   компонента. Не router.refresh и не revalidate: перезапрос списка — это лишний
   круг до сервера там, где всё уже известно.

6. Сиды: у Анны 3 задачи, у Бориса 2. Названия человеческие, не "test 1".

ЧТО ЕЩЁ ПОЛОЖИ В ПРОЕКТ

7. Схему базы накатывай через `prisma migrate dev --name init`, миграцию оставь
   в репозитории.

8. Файл README.md: как поднять, как войти, что где лежит, какие версии стоят.
   Коротко.

9. Скрипт scripts/break.ts с двумя режимами, который вносит настоящие поломки
   для тренировки. Поломки ОБЯЗАТЕЛЬНО живут на разных слоях — в этом весь смысл:
   - режим "owner" — ЛОМАЕТ СЕРВЕР: в запросе списка задач убирает условие
     по владельцу, так что каждый пользователь начинает видеть задачи всех;
   - режим "screen" — ЛОМАЕТ ТОЛЬКО КЛИЕНТ: компонент после успешного создания
     не добавляет задачу в свой список, и пользователь её не видит.
     Серверный код в этом режиме не трогается ВООБЩЕ: ответ корректный, запись
     в базе есть, перезагрузка страницы задачу покажет. Ломается ровно то,
     что видит человек в момент действия.
   Проверь себя: если в режиме "screen" ты правишь хоть один файл на сервере —
   ты сделал не то. Правится только клиентский компонент отрисовки.
   Оба режима должны уметь откатываться: scripts/break.ts --restore.
   Сохраняй оригиналы изменяемых файлов рядом, в scripts/.backup/.
   Правки вноси по точным строкам-якорям: поставь в коде комментарии-маркеры
   и упомяни их в README. Скрипты запускаются нативным Node 22 напрямую
   (`node scripts/break.ts`), без tsx и ts-node. Пропиши npm-скрипты для seed и break.

10. НЕ пиши никаких тестов и не ставь инструменты для тестов. Совсем.
   Приложение должно быть чистым — тесты я буду ставить отдельно, это
   и есть смысл упражнения.

КОГДА ЗАКОНЧИШЬ

Подними приложение, зайди под обоими пользователями и покажи мне:
что списки разные, что шестая задача не создаётся, что удаление чужой
задачи не проходит. Приложи вывод команд.

Дальше покажи ОБЕ поломки по очереди. Не одну, обе — если какая-то из них
не воспроизводится, полигон бесполезен, а узнаю я об этом в самый неподходящий
момент.

1. `scripts/break.ts owner` — Борис видит задачи Анны. Верни через --restore.

2. `scripts/break.ts screen` — создай задачу и покажи, что в списке её НЕТ.
   Страницу при этом НЕ перезагружай: после перезагрузки она появится,
   и это правильно — поломка именно в моменте.
   Отдельно покажи две вещи: что запись в базе есть и что сервер ответил
   корректно. Это и есть смысл режима — сервер здоров, а человек результата
   не видит. Верни через --restore.

Если вторая поломка не воспроизвелась — не подгоняй демонстрацию под неё,
а чини причину: скорее всего компонент не держит список в своём состоянии,
а перезапрашивает его с сервера.
```

## Дальше

Когда приложение поднимется — прогоняйте по нему промпты из файлов `00`…`08`,
как на своём проекте. А дойдя до пятого и шестого шага, попробуйте обе поломки:

- **после пятого** — `scripts/break.ts owner`. Проверки ответов приложения должны
  покраснеть. Обратите внимание, что код ответа при этом не изменился: сервер
  отвечает как обычно, ловит именно проверка состава списка.
- **после шестого** — `scripts/break.ts screen`. Теперь наоборот: проверки ответов
  зелёные, потому что сервер здоров, а браузерный тест красный, потому что человек
  задачу не видит.

Вот ради этой пары и нужен полигон. Два уровня проверок ловят разное, и увидеть
это можно только на приложении, которое не жалко сломать.
